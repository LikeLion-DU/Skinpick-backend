# 음식 × 피부 시계열 패턴 — 설계서

> 2026-08-18 · 대상: Skinpick-backend · **미구현 · 08-21 마감 범위 밖**
> 원래 "PR4" 로 계획했다가 PR1~3(#49 · #53 · #51 · #52) 머지 후 의도적으로 뒤로 미룬 기능이다.
> 이 문서는 **그 판단의 근거와, 다시 집었을 때 필요한 설계**를 남긴다.

## 0. 왜 지금 만들지 않았는가

세 가지를 저울에 올렸다.

1. **08-21 이 업로드 마감이고 그 안에 QA·배포·촬영이 들어간다.** 남은 필수 경로는 실기기 E2E → 발표 시나리오 검증 → 배포다. 읽기 전용 API 라 스키마 위험은 0 이지만, 마감 3일 전에 새 화면을 여는 것은 그 자체가 위험이다.
2. **표본이 없다.** 상관을 말하려면 최소 2주치 연속 기록이 필요한데 지금 DB 에 그만한 데이터가 없다. 발표에서 보여주려면 시드 데이터를 만들어야 하고, 그러면 "실제로 동작한다" 가 아니라 "만들어 둔 데이터로 그린다" 가 된다 — 이 제품이 재현성을 주장하는 방식과 어긋난다.
3. **교란 변수를 통제할 수 없다.** 수면·스트레스·물 섭취는 `AppUser` 에 **정적 프로필**로만 있다(§4). 날짜별 기록이 아니라 상관에서 빼낼 수가 없다.

> **그래서 발표에서는 "확장 포인트" 로 말한다.** 새 컬럼 하나 없이 지금 스키마로 계산이 된다는 것이 이 설계의 요점이고, 그건 데이터가 쌓이면 바로 열리는 문이라는 뜻이다.

## 1. 핵심 — 새 테이블도 새 컬럼도 필요 없다

이미 저장되고 있는 네 테이블이 계산에 필요한 것을 전부 갖고 있다.

| 테이블 | 쓰는 값 |
|---|---|
| `skin_analysis` | `created_at` · `hydration` `oil` `redness` `trouble` `barrier` · `skin_score` |
| `skin_plate` | `created_at` · `plate_score` |
| `food_analysis` | `sodium_mg` `sugar_g` `calories_kcal` · `cooking_method` · **`spiciness` `oiliness` `food_group` `processing_level`**(V7) |
| `skin_plate_feedback` | `rule_code` · `score_delta` — 어느 룰이 언제 걸렸는지 |

V7 이 더한 관찰 특성이 여기서 두 번째 값을 한다 — 룰의 강도 계수로 쓰이는 동시에, **패턴 분석의 집계 축**이 된다. `processing_level` 은 아직 점수에 쓰지 않지만 이 화면을 위해 쌓고 있는 값이다.

## 2. 무엇을 세는가

**트리거(그날 먹은 것) → 다음날 지표 변화**. 셋으로 시작한다.

| 트리거 | 판정 | 관찰 지표 |
|---|---|---|
| 고나트륨 | `Nutrition.isHighSodium()` (>1500mg) | 다음날 `redness` |
| 고당류 | `Nutrition.isHighSugar()` (>25g) | 다음날 `trouble` |
| 튀김·기름 | `cooking_method = FRIED` 또는 `oiliness = HIGH` | 다음날 `oil` |

**판정 함수를 새로 만들지 않는다.** `Nutrition` 의 기존 `isHigh*()` 를 그대로 쓴다 — 룰 엔진이 감점에 쓰는 것과 같은 경계여야, 화면의 "고나트륨" 과 점수의 "나트륨 과다" 가 같은 뜻이 된다.

### 날짜 짝짓기

- 일 경계는 **KST 달력일**(`DateRange`). 끼니 라벨(`MealType`)과 무관하다 — 기존 히스토리·리포트와 같은 규칙이다.
- "다음날" 은 `D+1` 의 **그날 최신 분석**(`skin_analysis` 를 날짜별로 접어 마지막 것). `PlateHistoryService.skinScorePerDay` 와 같은 방식이다.
- **양쪽이 다 있는 날만 센다.** D 일에 음식 기록이 있고 D+1 에 피부 분석이 있어야 한 표본이다. 없는 날을 0 이나 평균으로 채우면 그 순간 숫자가 거짓이 된다(일일 리포트가 안 찍은 끼니를 안 세는 것과 같은 원칙).

### 변화의 기준선

D+1 의 지표를 **그 사용자의 기간 중앙값**과 비교한다. 절대값(예: 홍조 60 초과)으로 하면 원래 홍조가 높은 사람은 항상 "패턴 있음" 이 되고, 낮은 사람은 영영 안 뜬다.

## 3. 레벨 게이팅 — 표본이 부족하면 말하지 않는다

| Level | 조건 | 화면 |
|---|---|---|
| **0** | 짝지어진 표본 < 5 | "아직 음식과 피부의 관계를 볼 만큼 기록이 부족해요" |
| **1** | 표본 ≥ 5, 일치율 < 60% | "최근 5회 중 2회에서 비슷한 변화가 관찰됐어요" — 관찰만 |
| **2** | 표본 ≥ 5, 일치율 ≥ 60% | "고나트륨 음식을 먹은 다음날 붉은기가 높아지는 경향이 있어요" |
| ~~3~~ | — | **범위 밖.** 패턴 → 오늘의 추천 연결 |

임계값(5 · 60%)은 `PatternConstants` 한 파일에 둔다 — `RuleConstants` 와 같은 이유다.

> **Level 0 을 빈 화면으로 두지 않는다.** 기록이 부족하다는 것도 정보이고, 며칠 더 기록하면 열린다는 신호가 된다.

## 4. 표현 규칙 — 상관이지 인과가 아니다

```
좋음:  최근 6회 중 4회에서 고나트륨 음식을 먹은 다음날
       붉은기가 평소보다 높게 기록됐어요.

나쁨:  나트륨 때문에 홍조가 생겼습니다.
```

- **문장은 템플릿이다. AI 가 만들지 않는다.** 같은 입력이면 같은 문장 — `PlateCommentPrompt` 의 `reason` 과 같은 결정론이다. AI 를 쓸 이유가 없다: 숫자를 그대로 끼우는 문장이고, 여기서 모델이 한 걸음이라도 나가면 그게 곧 인과 단정이다.
- 허용 표현: `~가 함께 기록됐어요` · `~경향이 있어요` · `~패턴이 관찰됐어요` · `영향을 줄 수 있어요`
- 금지: `~때문에` · `~를 유발` · 의학적 진단·치료 표현 (PRD §18.9 와 같은 규칙)
- **표본 수를 항상 함께 보여준다.** "6회 중 4회" 없이 "경향이 있어요" 만 쓰면 3일치로 단정하는 것처럼 읽힌다.

### 통제하지 못하는 것을 밝힌다

수면·스트레스·물·생리 주기·계절 — 전부 피부 지표를 움직이는데 이 계산은 하나도 통제하지 않는다. 화면 하단에 한 줄로 남긴다: "음식 외에도 수면·컨디션 등 여러 가지가 함께 영향을 줍니다."

## 5. 구조

```
GET /api/v1/patterns/food-skin?from=&to=      (기본: 최근 30일 · 상한 90일 — DateRange)
  ↓
FoodSkinPatternController  (@CurrentUser Long userId)
  ↓
FoodSkinPatternService     @Transactional(readOnly = true)
  ├─ SkinPlateRepository.findInRange(...)          ← 기존 메서드 그대로
  └─ SkinAnalysisRepository.findByUserIdAndCreatedAt...(...)  ← 기존 메서드 그대로
  ↓
FoodSkinPatternCalculator  ← DB·Spring 모르는 순수 계산
  ↓
FoodSkinPatternResponse(List<PatternDto>)
```

- **계산기는 순수 함수다.** `DailyReportAssembler` 와 같은 자리 — 입력이 엔티티 목록, 출력이 DTO. 그래야 시계열 픽스처로 단위 테스트가 된다.
- **새 리포지터리 메서드가 필요 없다.** `findInRange`(`@EntityGraph` 로 `foodAnalysis` 를 함께 읽는다)와 피부 기간 조회가 이미 있다.
- AI 호출 없음 · 쓰기 없음 · 캐시 없음. 조회할 때마다 다시 세도 같은 값이고, 90일 × 사용자 1명은 순수 계산으로 충분히 싸다.

### 응답 모양

```jsonc
{ "from": "2026-07-20", "to": "2026-08-18",
  "patterns": [
    { "trigger": "HIGH_SODIUM", "metric": "REDNESS",
      "level": 2, "sampleCount": 6, "matchCount": 4,
      "message": "고나트륨 음식을 먹은 다음날 붉은기가 높게 기록되는 편이에요.",
      "detail": "최근 6회 중 4회에서 관찰됐어요." }
  ] }
```

`level` 0 이면 `patterns[]` 는 트리거별로 내려가되 `matchCount` 없이 안내 문구만 싣는다 — 앱이 "무엇을 더 기록하면 되는지" 를 보여줄 수 있어야 한다.

## 6. 하지 않을 것

- **점수에 반영하지 않는다.** 패턴은 표시 전용이다. 개인별 가중치로 룰을 흔들기 시작하면 "같은 사진 = 같은 점수" 가 깨진다.
- **사용자별 학습 모델을 만들지 않는다.** 카운팅과 중앙값 비교가 전부다.
- **통계적 유의성을 주장하지 않는다.** p-value 도 신뢰구간도 쓰지 않는다 — 표본이 한 자릿수인데 그런 수치를 붙이면 없는 엄밀함을 흉내내는 것이다.

## 7. 다시 집을 때 함께 볼 것

| 항목 | 왜 |
|---|---|
| 날짜별 습관 기록 | 지금은 `AppUser` 정적 프로필뿐이라 교란 변수를 통제할 수 없다(§0-3) |
| `skin_analysis` 일별 스냅샷 뷰 | "그날의 대표 지표" 정의가 지금은 조회 코드마다 흩어져 있다 |
| 사용자 피드백("맞아요/아닌 것 같아요") | 패턴의 체감 정확도를 재는 유일한 방법. 개인화의 다음 단계 재료 |
| Level 3 (패턴 → 오늘의 추천) | `RecommendationService` 가 음식 기록을 보게 되는 지점. 추천 → 섭취 → 결과 루프가 여기서 닫힌다 |
